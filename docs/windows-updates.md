# Windows updates in controlled mode

This guide covers updating the **Codex Desktop Windows package**. [Claudex controller and userscript updates](userscripts.md#url-sources-and-installation) use separate source files, tools, and schedules. Changing **Automatic checks** or a script's **Check updates** preference in **Claudex - User scripts** does not change this companion's startup/15-minute package-check cadence.

Packages containing Windows services can require administrator approval. On Windows error `0x80073D28`, Claudex retries only the package operation through a UAC prompt. Approve using the same Windows account; another administrator account is rejected to avoid registering Codex for the wrong user. Staging and final installation may each prompt. Cancelling staging leaves Codex open; cancelling after Codex exits reports the failure and the controller attempts to reopen the existing installation. Codex and its controller remain unelevated. Other deployment errors do not trigger elevation.

The controlled Windows launcher preserves Codex's packaged production identity and default profile, adding only the local DevTools arguments. It does not require the `dev` build flavor or disable Codex's native updater. Claudex supplies a separate **Updates** panel during controlled Windows launches. It checks OpenAI's stable release manifest on startup and every 15 minutes. Select **Update and restart now** to download and stage the signed MSIX, quit Codex normally, install, verify the registered version, and reopen in controlled mode with userscripts restored. Active work can be interrupted by the restart; Codex's normal quit confirmation remains in effect.

The updater runs outside Codex's package/job lifetime. It waits until no processes have the Codex package identity for two continuous seconds before registration. Cancelling quit or leaving a process running aborts installation after 60 seconds. It retries only package-in-use errors, at most twice, and records failures in `%APPDATA%\claudex-yourself\updates\status.json`. After graceful shutdown, a package-in-use retry can ask Windows to finish shutting down remaining target package activity through `ForceTargetApplicationShutdown`. Other errors are not retried. It does not change Windows package permissions. The downloaded package's identity, publisher, architecture, and version must match the selected candidate before Windows validates its signature during staging.

The panel acknowledges clicks immediately, keeps the install action disabled until the worker responds, and shows download progress. Release checks run in the background so they do not block progress updates. The launcher keeps its controlled startup environment active until the main Codex renderer and preload bridge are ready, then restores normal Windows package debugging settings. Update completion is recorded only after that readiness check; activating an ordinary Codex window is insufficient. The first installation attempt shares the existing shutdown quiet period instead of adding a second fixed delay.

If the initial controlled relaunch times out but Codex subsequently becomes ready, the watcher rechecks recovery on later polls and later launches. It clears only a restart failure, after confirming the installed version reached the update target and the live renderer and quit bridge are ready. Recovery waits until the installation worker releases its operation lock. New failures record a stable failure kind; existing status files with either historical timeout message are also recognized. Installation and unrelated failures remain visible.

The updater chooses the **newest obtainable version**, comparing Store delivery with the official version-specific and stable download URLs, package manifests in its local cache, and Windows staging. The installed version is the minimum: it never installs a downgrade or reinstalls the current version. For example, with 5003 installed, 6511 announced, and 5280 downloadable or already staged, it offers 5280 and also checks Store availability. With 5280 already installed and no newer verified package or Store update, it shows the unfulfilled 6511 announcement without offering another installation. An obtainable version-specific release takes precedence over an older stable alias, and a stable package newer than the announcement is eligible too. Check results expose `announcedVersion` separately from the selected `availableVersion`. Failures checking individual sources stay visible.

HTTP headers are checked before downloading and again on the GET response before reading the installer body. Full package manifest and Windows signature checks remain required. Rejected downloads retain an HTTP receipt; an unchanged ETag prevents another full download. Cache entries are identified by their actual package manifests rather than their filenames, allowing a valid older download saved under an announced version's name to be reused. If the selected source changes or remains a rejected candidate, **Update pending** disables installation until **Check again** finds a usable source.

The release feed is a Store announcement; direct MSIX downloads are separate deployment sources and can publish at different times. Claudex checks both **Microsoft Store** and the native version-specific and stable direct MSIX URLs, plus its cache and existing Windows staging. Store checks use `StoreContext.GetAppAndOptionalStorePackageUpdatesAsync` in a short-lived helper with Codex's package identity, launched through `Invoke-CommandInDesktopPackage`. The helper verifies its identity and only requests updates for the stable Codex package. Windows restrictions or Store errors remain visible while direct downloads remain usable.

An information-only check never starts a Store download. Store availability is returned separately in `store.hasUpdate` and `store.canSilentlyDownload`: the Store API describes the installed package and does **not** expose the target version before downloading. `availableVersion` remains the newest verified candidate; a Store-only update can therefore have `updateAvailable: true` while `availableVersion` equals the installed version. The panel explains that the Store target will be verified. The announced version is never treated as proof of the Store target.

On **Update and restart now** or `update prepare`, Claudex downloads an eligible Store update with `TrySilentDownloadStorePackageUpdatesAsync`, without installing or closing Codex. It then checks both direct URLs and the protected staged manifests again and selects the highest actual version across all obtainable sources. A newer direct package wins over an older Store package; a newer Store package wins over lagging direct downloads, including when it differs from the announcement. Installation uses the verified selected version. Store download failures remain visible and allow a verified direct package to be used. If no newer verified candidate can be found, Codex stays open. Silent Store downloads respect Store automatic-update settings and network restrictions; the panel explains when these prevent Store delivery.

Current availability and newer announcements take precedence over historical completion messages. A completed operation is shown only until a newer check arrives and only when its target matches the installed version. Older failures remain identified as previous attempts alongside fresh availability; they do not replace it. If a release is announced but no newer package can be obtained, the panel shows **Update pending** and the announced version rather than claiming that the old successful update is current.

If a staged package disappears between checking and pressing Update, the worker reports **waiting**, explicitly says Codex was left open, and does not claim the update succeeded. Update state transitions are retained in `updates/history.jsonl`, and detached worker output and exception details are retained in `worker-logs/update-worker.log`. Later checks no longer erase the only evidence of a failed attempt. Both `0x80073D02` and the Store's `0x800700E9` package-in-use result receive the bounded shutdown recovery; quit cancellation still prevents installation.

Store checks start through a small Windows Script Host GUI launcher, which creates PowerShell hidden at process creation. This avoids the brief console flash caused by PowerShell's own `-WindowStyle Hidden` option. Store eligibility checks require Windows Script Host/VBScript support; if unavailable or disabled, the failure remains visible and direct download checks remain usable. The update watcher also restores the four Claudex taskbar quick actions when it starts, including after a controlled relaunch. Restoration errors are recorded in `taskbar-error.txt`.

If Windows has already staged a newer version (including an intermediate release older than the current announcement), the updater includes that protected package as a candidate and registers it after shutdown when selected. It checks the announced version plus package names from the latest 2,048 Windows deployment events. Each candidate must have a real protected manifest matching Codex's identity, publisher, architecture, and version; event records alone never authorize installation. It uses the normal user's registered package location without enumerating WindowsApps or querying other users' packages as an administrator. Cleared or older deployment history can limit discovery; failures reading history remain visible. If no verified candidate is newer than the installed version, Codex stays open.

```powershell
claudex-yourself update check     # Inspect installed and available package versions
claudex-yourself update prepare   # Download, validate, and stage; leave Codex running
claudex-yourself update install   # Download if needed, quit, install, and restart controlled Codex
claudex-yourself update status    # Read persisted progress or failure
claudex-yourself update restart-test # Real graceful quit/relaunch with package operations mocked
```

`update restart-test` is a disruptive diagnostic: it closes and reopens Codex through the same detached worker, graceful quit, full-exit check, and controlled launcher as a real update. It does not query remote update sources, download, stage, or install a package. It verifies that the installed version remains unchanged, preserves normal quit confirmation, and labels its result as a mock test in the persisted status and history. Use it only when ready to restart active sessions.

The MCP equivalents are `check_codex_update`, `install_codex_update`, and `get_codex_update_status`. Installation requires a reachable controlled renderer for graceful quit. Ordinary Codex launches keep their normal behavior. This companion updater currently supports the stable `OpenAI.Codex` Windows package on x64 and Arm64; macOS uses Codex's native updater, with [Claudex's relaunch watcher](../README.md#2-launch-codex) restoring controlled mode after eligible native updates. The update panel is a reversible registered userscript (`codex_updates`), loaded by the launcher's companion worker rather than the per-user autoload list. A URL update of a per-user `codex_updates.js` file concerns JavaScript source, not a Windows package update; the standard companion worker loads its bundled copy from `bin/scripts/`. No new Codex build is marked tested just because installation succeeds.
